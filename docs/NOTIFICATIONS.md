# Notification channels, escalation policies and delivery log (M5.01)

M5.01 models where notifications go and when, and gives owners and admins a page to manage it. Adapters that actually deliver (M5.02), delivery jobs with deduplication and retries (M5.03), escalation timing and cancellation (M5.04) and quiet hours (M5.05) build on this model. Evidence is in [TASKS.md](TASKS.md); the route permissions are in [AUTHORIZATION-MATRIX.md](AUTHORIZATION-MATRIX.md).

## User decisions

- **Roles**: only owners and admins create, change, verify, activate and delete channels and escalation policies; members and viewers see the lists with masked destinations. Choosing one of the existing policies for a monitor is monitor configuration and stays with `MonitorPolicy::update` (owners, admins, members).
- **Verification**: a channel is created inactive. A six-digit code is sent through the channel itself; typing it back verifies and activates the channel. Changing the destination or a credential discards the verification and pauses the channel.
- **Escalation**: one policy may be the team default; each monitor may override it (`monitors.escalation_policy_id`). With neither, the monitor notifies nobody and the page warns about it.

## Data model

Migrations `2026_10_29_000017_create_notification_tables.php` and `2026_10_29_000018_add_escalation_policy_to_monitors.php`. All tables are tenant-owned (`BelongsToTeam`, `team_id` from the context, composite foreign keys).

| Table | Purpose | Main constraints |
|---|---|---|
| `notification_channels` | Type, label, encrypted configuration, `is_active`, `verified_at`, pending-code digest, expiry, attempts and last send | Type in the five families; label 1–100 characters; active ⇒ verified; digest and expiry both set or both null |
| `escalation_policies` | Label, `steps_json`, `is_default` | Label unique per team ignoring case; at most one default per team (partial unique index); 1–20 JSON steps (the action limits it to 5) |
| `notification_logs` | One row per delivery: incident, channel (nullable), channel type snapshot, kind, step, status, attempts, redacted response, dedupe key, `sent_at` | Dedupe key unique per team; status `sent` ⇒ `sent_at`; response ≤ 1000 characters; deleting the channel sets `channel_id` null and keeps the row |
| `monitors.escalation_policy_id` | Optional override | Composite key to a policy of the same team; deleting the policy clears only the override |

Delivery logs are modelled and shown on the incident page now; M5.03 writes them. `kind` is `opened`, `escalated` or `resolved`; `status` is `pending`, `sent`, `failed` or `suppressed` (`NotificationKind`, `DeliveryStatus`).

## Channel configurations

`ChannelConfigurationParser` is the single rule set for every entrypoint and needs no network. Each family is an immutable DTO implementing `ChannelConfiguration` (`toArray()` with secrets, `hint()` masked for everyone, `editable()` non-secret values for managers, `sameAs()`).

| Family | Fields | Secret | Hint |
|---|---|---|---|
| Email | `address` (RFC, lower-cased, ≤ 254 bytes) | — | `o•••@example.test` |
| Slack | `webhook_url` (HTTPS under `hooks.slack.com/services/`) | URL | `hooks.slack.com/services/…WXYZ` |
| Telegram | `bot_token` (`<id>:<secret>`), `chat_id` (numeric or `@name`) | token | `Chat …7890` |
| Webhook | `url` (absolute HTTPS, no userinfo or fragment); `signing_secret` generated by the server | URL and key | scheme and host only |
| SMS (stub) | `phone` (E.164) | — | `+•••1234` |

- The whole configuration is stored in one `encrypted:array` column and hidden from Eloquent serialization. Pages receive only `NotificationPresenter` projections.
- On edit, a blank secret field keeps the stored secret, so forms never receive secrets back. The type cannot change.
- URL syntax reuses `MonitorInputSyntax::url()`. It authorizes no destination: the delivery adapters must re-run the SSRF guard ([OUTBOUND-SECURITY.md](OUTBOUND-SECURITY.md)) at every attempt (M5.02).
- The webhook signing key is a 256-bit hex value. It is shown only through `POST …/signing-secret`, which rotates it and returns it once as non-cacheable JSON, never in Inertia props or the session (same pattern as heartbeat credentials). Rotation keeps the verification, because the destination is unchanged.
- Error messages never echo submitted values. `config` and `code` are in the global `dontFlash` list of `bootstrap/app.php`, so neither Form Request failures nor domain refusals rethrown by controllers put them in the session.

## Verification lifecycle

`ManageNotificationChannels` locks Team → channel and re-runs `NotificationChannelPolicy` for every change.

1. **Send** (`sendVerification`): refused within `verification_resend_seconds` (60 s) of the last send. A fresh code is generated, its HMAC (`ChannelVerificationCodes`, keyed by the application key and bound to the channel identity) is committed with a 15-minute expiry and zero attempts, then the message is sent **outside the transaction** through the `ChannelVerificationSender` contract. If the sender fails, that code is withdrawn (only if it is still the current one) and the cooldown is freed.
2. **Confirm** (`confirmVerification`): no pending or expired code → refusal. A correct code sets `verified_at`, activates the channel and clears the code. A wrong code is counted and **committed before** the refusal; the fifth wrong code discards the code, and a new one must be requested.
3. **Activate/pause** (`setActive`): activating requires `verified_at`; pausing is always allowed.
4. **Edit** (`update`): a label change keeps everything; any destination or credential change resets `verified_at`, deactivates the channel and discards a pending code.
5. **Delete**: refused while any policy step references the channel, naming those policies; delivery logs survive with `channel_id` null.

Until M5.02 the container binds `UnavailableChannelVerificationSender`, which refuses with "Delivery to <type> channels is not available yet." The page shows that refusal; no channel can be verified in the running application before the adapters exist. Tests bind `Tests\Support\RecordingVerificationSender`.

Brute force: five guesses per code and one code per minute limit an admin to about 7,200 guesses per day against a million values, and every new code is a visible message to the destination owner. Only owners and admins can try at all.

## Escalation policies

`ManageEscalationPolicies` validates under the Team lock:

- 1–5 steps (`steps_per_policy`); delays are absolute minutes from the incident confirmation, 0–1440, **strictly increasing**;
- each step notifies 1–10 distinct channels (duplicates in a step are removed); every channel must belong to the team (the tenant scope hides foreign ones), inactive channels are allowed so a policy can be prepared before verification, and deliveries will skip them;
- labels are unique per team ignoring case; at most 10 policies per team;
- marking a policy as default clears the previous default in the same transaction.

`AssignEscalationPolicy` sets or clears a monitor override after Team → monitor locks and `MonitorPolicy::update`; it refuses a policy outside the team and never touches execution state (`execution_revision`, `next_check_at`). `EscalationPolicyResolver::forMonitor()` returns the override, then the default, then null; M5.03/M5.04 will call it.

Steps reference channels by identity in JSON, as in the specification. Channel deletion and policy changes share the Team lock, so a policy cannot keep a reference to a channel deleted concurrently.

## Routes and pages

`routes/notifications.php`, in the `auth`, `verified`, `EstablishTeamContext` group. Error keys: `config.<field>` for configuration, `channel` for channel refusals, `policy` for policy refusals.

| Route | Method and URL | Roles |
|---|---|---|
| teams.notifications.index | GET /teams/{team}/notifications (no-store) | all members |
| teams.notification-channels.store | POST /teams/{team}/notification-channels | owner, admin |
| teams.notification-channels.update | PATCH …/notification-channels/{channel} | owner, admin |
| teams.notification-channels.destroy | DELETE …/notification-channels/{channel} | owner, admin |
| teams.notification-channels.verification.store | POST …/{channel}/verification | owner, admin |
| teams.notification-channels.verification.confirm | POST …/{channel}/verification/confirm | owner, admin |
| teams.notification-channels.activation | PATCH …/{channel}/activation | owner, admin |
| teams.notification-channels.signing-secret | POST …/{channel}/signing-secret (JSON, no-store) | owner, admin |
| teams.escalation-policies.store | POST /teams/{team}/escalation-policies | owner, admin |
| teams.escalation-policies.update | PATCH …/escalation-policies/{policy} | owner, admin |
| teams.escalation-policies.destroy | DELETE …/escalation-policies/{policy} | owner, admin |
| teams.monitors.escalation-policy | PATCH /teams/{team}/monitors/{monitor}/escalation-policy | owner, admin, member |

- `Notifications/Index` lists channels (state, masked hint, verification expiry, policies using them) and policies (steps with delays and inactive channels marked), with empty states, a warning when monitors notify nobody, and the create/edit forms for managers. Bounds come from `config/notifications.php` through the `limits` prop.
- The monitor detail page has a **Notifications** section (`EscalationPanel`) with the effective policy and, for monitor managers, a selector whose empty value follows the team default.
- The incident detail page has a **Notifications sent** table (`DeliveryLog`, at most 100 rows, oldest first) without dedupe keys; a deleted channel shows its family only.
- Links to the page were added to the team and monitor list navigation.

## Limits of this task

- No adapter, job, delivery, deduplication, retry, escalation timer, maintenance silencing or quiet hours: M5.02–M5.05.
- Verification messages cannot be delivered until M5.02 binds real adapters; the SMS stub will record without sending.
- Verification is synchronous in the request; M5.02 adapters must bound their timeouts.
- No real browser test; focus does not move after a refusal (same limit as the incident pages).
