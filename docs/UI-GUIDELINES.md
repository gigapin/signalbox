# UI guidelines — Signalbox

UI.01.3 introduce token e primitive condivise, basate sui [percorsi UI.01.2](USER-DASHBOARD.md) e sull’inventario UI.01.1. Implementazione in [app.css](../resources/css/app.css) e [components/ui](../resources/js/components/ui). Non introduce AppLayout, nuove rotte, librerie o metriche. Le pagine saranno migrate in UI.02–UI.04; badge monitor/incidenti e viewport tabellare adottano già la base condivisa.

## Token e composizione

Tema scuro iniziale: canvas blu scuro, superfici rialzate, azione primaria lilla, stati semantici verde/ambra/rosa/azzurro. Nome testuale da configurazione e identità definitiva restano nel proprio task; non introdurre loghi. I token `--color-ui-*`, `--spacing-ui-*`, `--text-ui-*`, `--font-ui` e `--radius-ui` sono dichiarati con Tailwind `@theme`, senza cambiare i token esistenti. Le regole sono circoscritte a classi `ui-*`: nessuno stile globale di input, link o body altera i temi delle status page pubbliche.

| Token/gruppo | Valori e uso |
|---|---|
| canvas / surface / raised | `#0b1220` / `#152033` / `#202e44`; sfondo shell, pannelli, stato neutro |
| text / muted | `#f1f5fb` / `#b5c3d8`; testo primario e istruzioni, mai opacity per rendere secondario un dato importante |
| border / focus | `#72849e` / `#b9a4ff`; confini dei controlli, ring di 2 px con offset 3 px |
| accent / accent-hover / on-accent | `#b9a4ff` / `#cbbcff` / `#15102a`; azioni primarie, testo scuro sul pulsante |
| success / success-bg | `#9be2ba` / `#12352b` |
| warning / warning-bg | `#f9d48a` / `#3d2c17` |
| danger / danger-bg | `#ffb4bb` / `#44202c` |
| info / info-bg | `#a8d8ff` / `#172f49` |
| Tipografia | Font di sistema senza download; body 1 rem, testo secondario/badge 0.875 rem, h2 1.25 rem, h1 1.875 rem; line-height corpo 1.5 |
| Spaziatura | Scala 0.25 / 0.5 / 0.75 / 1 / 1.5 / 2 rem, padding pannelli 1.5 rem; controlli almeno 2.75 rem (44 px con root standard) |
| Angoli | Raggio 0.625 rem per controlli, badge e superfici |

`ui-theme` è la base opt-in per il futuro layout: applica canvas, testo e font; non crea sidebar o navigazione. Le utility Tailwind semantiche come `bg-ui-surface` e `text-ui-muted` sono disponibili attraverso i token. Le primitive possiedono già i propri colori di superficie. Nuovi elementi non devono introdurre colori arbitrari per gli stessi significati.

Contrasto: testo normale almeno **4.5:1**, confini dei controlli e indicatori focus almeno **3:1** rispetto alle superfici adiacenti previste. [UiContrast.test.ts](../tests/frontend/UiContrast.test.ts) legge i valori CSS effettivi e verifica luminanza sRGB, testo primario/secondario/link/errori sui tre sfondi, tutti gli stati e hover primario, bordi e focus. Queste verifiche numeriche non certificano una pagina futura o sostituiscono VoiceOver/zoom/browser. Nuove combinazioni di sfondo/foreground richiedono una verifica della coppia; non usare overlay/opacità che cambino il colore effettivo senza misurarlo.

## Contratti delle primitive

Le primitive presentano contenuti forniti dal chiamante: non caricano dati, non possiedono policy, non ritentano richieste e non calcolano SLA. Importare i componenti dai rispettivi file senza una nuova dipendenza UI.

| Componente | Interfaccia e comportamento | Responsabilità del chiamante |
|---|---|---|
| [Button](../resources/js/components/ui/Button.tsx) | Attributi/ref nativi; `variant` primary/secondary/danger, `busy`, `busyLabel`. Default `type="button"`; busy imposta disabled e aria-busy, sostituendo il testo con Working… o label fornita | Submit esplicito con `type="submit"`; pending dalla richiesta; etichetta concreta (“Saving monitor…”), motivo di blocco leggibile vicino al comando; conferma distruttiva e autorizzazione esterne |
| [InputField](../resources/js/components/ui/InputField.tsx) | Props/ref nativi input con `label` obbligatoria, `hint`, `error`; ID automatico o esplicito. Label required testuale, aiuti/errori uniti ad aria-describedby preesistente; errore imposta aria-invalid e regione polite stabile | Usare per input testuali/numerici/data/password. Checkbox/radio, hidden e upload richiedono composizione nativa appropriata, non questo campo. Nome/value/onChange/limiti e validazione appartengono al form; nessuna persistenza o sanificazione silenziosa |
| [Panel](../resources/js/components/ui/Panel.tsx) | Section nominata dal titolo con ID univoco, headingLevel 2 predefinito o 3 se annidato; description facoltativa | Scegliere gerarchia heading corretta; fornire caricamento, vuoto, errore o contenuto; nessun finto dato per riempire il pannello |
| PageHeading, nello stesso file | Un h1, description e actions che vanno a capo | Un solo PageHeading per pagina; il layout imposta separatamente document title; azioni già filtrate dai permessi |
| [Badge](../resources/js/components/ui/Badge.tsx) | Testo con tone neutral/success/warning/danger/info; nessun live region | Etichetta esplicita e significato di dominio. Stato osservato e operativo restano distinti; colore non sufficiente |
| [Alert](../resources/js/components/ui/Alert.tsx) | title/children, tone, `announce` off/polite/assertive; statico per default, role status/alert solo su richiesta | Polite per conferme nuove, assertive per errori bloccanti nuovi; non annunciare ogni badge o intera pagina ad ogni evento. Nessuna eccezione grezza/credenziale nei children; eventuali retry/dismiss sono comandi espliciti del chiamante |
| [DataTable](../resources/js/components/ui/DataTable.tsx) | caption visibile, indicazione di scorrimento, TableScrollArea focusabile/nominata, tabella nativa con children thead/tbody/tfoot | th con scope col/row, link nominativi, nessuna colonna indispensabile nascosta; filtri/paginazione e vuoto fuori dalla tabella. L’overflow resta locale |
| [TableScrollArea](../resources/js/components/TableScrollArea.tsx) | Conserva `label`/`children`; aggiunge `describedBy` opzionale per istruzioni esterne, focus semantico condiviso | Riutilizzabile dalle tabelle legacy senza ricostruire markup o nomi accessibili |

Le classi `ui-input` e `ui-label` possono accompagnare select/textarea nativi con label, aiuti ed errori correttamente associati; non esiste un wrapper che inventi opzioni o risposte server. `ui-link` mantiene underline e focus per link nativi o Inertia: la navigazione resta un link, l’azione resta un button. Non aggiungere un finto link disabilitato per una rotta assente. Comporre una famiglia nuova soltanto quando un flusso reale ne richiede il comportamento.

Adozione iniziale: [MonitorBadges](../resources/js/components/monitors/MonitorBadges.tsx) e [IncidentBadges](../resources/js/components/incidents/IncidentBadges.tsx) mappano stati noti ai toni condivisi conservando i label helper; valori sconosciuti restano testo con tono neutral. Up/Down/Unknown non sono sinonimi di active/paused/suspended, e un incidente resolved non indica uptime 100%. Non vengono cambiate policy o proiezioni.

## Contenuti, accessibilità e stati

- Etichette in inglese con verbi specifici (“Create monitor”, “Pause monitor”), nome risorsa accanto alle azioni distruttive e distinzione “Public”/“Private” per gli aggiornamenti. Niente abbreviazioni senza contesto o solo icone per i comandi essenziali.
- Esplicitare unità e finestra: ms per latenza, s o testo esteso per intervalli/durate, % per percentuali e relativa copertura. Zero è una misura; null si presenta come assenza/indisponibilità, mai come 0 o 100. La primitive non converte né aggrega metriche.
- Date con `time dateTime` ISO e fuso visibile. Grafici attuali in UTC; report mensili nel fuso del team. Se si usa tempo relativo, affiancare un istante assoluto accessibile; nessuna data locale senza indicazione del fuso. La politica delle finestre/retention appartiene ai servizi metrici.
- Ordine heading e DOM seguono UI.01.2. Non eliminare outline; focus-visible con ring offset, gestione OS dei colori forzati conservata. Le primitive non hanno animazioni o timer decorativi. Errori inline polite e label persistente: il placeholder non è il nome del campo.
- I controlli disabled/busy conservano contrasto leggibile e bordo tratteggiato; il contesto deve spiegare perché non si può agire. Un pulsante occupato blocca l’attivazione, ma non dimostra idempotenza server: la richiesta e la sua gestione restano del chiamante.
- PageHeading e azioni vanno a capo; nomi e testi lunghi possono spezzarsi. Schede senza altezza fissa e tabelle con overflow locale. Sidebar da 1024 px/menu mobile e colonna contestuale da 1280 px saranno implementati in UI.02/UI.03, con prova a 390 px e zoom 200%.
- Stato vuoto come testo e azione consentita dentro Panel; caricamento con aria-busy sulla regione interessata e testo accessibile; errore con Alert e comando esplicito di recupero. Nessun auto-focus o annuncio totale ad ogni refresh realtime; il focus dopo navigazione/applicazione filtri spetta al layout/pagina.
- RequestFailureNotice resta montato una sola volta dall’app. Alert non lo sostituisce né aggiunge retry, recupero automatico, dismiss o reset dei draft. Revoca e cambio team non possono lasciare dati privati visibili: coordinamento e conferme d’abbandono restano ai task layout/flussi.

## AppLayout — UI.02.1

[AppLayout](../resources/js/components/app/AppLayout.tsx) è la shell privata per pagine di un team già autorizzato dal server. La prima adozione è [Dashboard/Show](../resources/js/pages/Dashboard/Show.tsx): il menu locale è stato rimosso e report, selezione grafici, metriche e hook realtime restano della pagina. Le altre viste mantengono temporaneamente AuthLayout fino alla migrazione UI.02.4; le pagine pubbliche e di autenticazione non vengono avvolte automaticamente dalla shell.

| Input | Contratto |
|---|---|
| `team` | `{ id, name }` del team della rotta, obbligatorio; nessuna inferenza da `currentTeamId` o dal team preferito |
| `section` | dashboard/monitors/incidents/notifications/status-pages/team; distingue la famiglia corrente anche per dettaglio e modifica |
| `title`, `description`, `actions`, `children` | Unico h1/document title, contesto facoltativo, comandi già autorizzati e contenuto della pagina |
| `ancestors` | Array facoltativo di `{ label, href }` costruito dall’applicazione; la shell antepone il team e aggiunge il titolo corrente non cliccabile. Non passare input `returnTo` grezzo |
| Props condivise Inertia | `appName`, `auth.user`, `status` già esistenti. Il menu account si mostra quando l’identità è presente; Admin richiede `isPlatformAdmin === true`. Nessun nuovo campo backend |

[navigation.ts](../resources/js/components/app/navigation.ts) costruisce sei destinazioni reali del team: Dashboard, Monitors, Incidents, Notifications, Status pages e Team. Una sola voce ha `aria-current="page"`; il breadcrumb ha separatamente il proprio elemento corrente. Non mostrare Maintenance, Billing o API prima delle rispettive pagine. Le voci sono collegamenti di lettura consentiti ai viewer: non implicano permessi di mutazione.

La shell riusa `ui-theme`, PageHeading e Alert per lo status condiviso. Il nome prodotto è testuale da `appName`, con link alla dashboard del team corrente. Skip link verso il main focusabile, landmark e heading sono presenti. La sidebar da 1024 CSS px occupa una colonna di 15 rem, rimane nel flusso della griglia ed è scorrevole su schermi bassi. Sotto soglia, la stessa navigazione è per ora visibile sopra il contenuto e va a capo: è una fase intermedia funzionante, il dialogo mobile e la sua gestione focus appartengono a UI.02.3. Selettore, ruolo corrente e cambio team sono UI.02.2; la shell non li simula.

[AccountMenu](../resources/js/components/app/AccountMenu.tsx) è una disclosure con button/aria-expanded/aria-controls, link nativi Inertia e normali Tab: non usa role menu. Contiene Your account, Your teams, Account security, Admin per operatori e un form POST Sign out. Escape chiude e ripristina il focus al trigger; click esterno chiude senza spostare il focus; navigazione chiude la disclosure. I listener sono rimossi alla chiusura/unmount. Logout usa `useForm`, payload vuoto e stato busy; nessuna GET di logout o replay automatico. La visibilità Admin è soltanto una proiezione: middleware/controlli server esistenti rimangono autorevoli, indipendentemente dal ruolo tenant.

[AppLayout.test.tsx](../tests/frontend/AppLayout.test.tsx) copre team esplicito contro preferenza differente, tutte le sezioni correnti, breadcrumb, branding configurabile, skip link, conservazione bozza, tastiera/Escape/click esterno, diniego del link Admin per i quattro ruoli tenant, presenza per flag operatore, navigazione e logout POST singolo durante pending. Suite Dashboard e RealtimePages verificano anche il primo utilizzo reale della shell. Test DOM e CSS non attestano un collaudo browser o la navigazione uniforme sulle viste ancora da migrare.

## Selettore team — UI.02.2

[TeamNavigation](../app/Services/Identity/TeamNavigation.php) restituisce `teamNavigation: { teams: [{ id, name, role }], selectedTeamId }` nelle pagine private `teams.*`, account e sicurezza di utenti verificati. Negli altri contesti la prop è null: niente elenco membership in home, accesso, inviti pubblici, status page pubbliche o pannello operatore. La preferenza viene riletta dal database e accettata solo se ancora presente fra le membership; nessuna scelta automatica del primo team. Il servizio usa due query indipendenti dal numero di team, non serializza modelli né carica configurazioni tenant. `/teams` mantiene anche le props preesistenti `teams` e `currentTeamId`, ora ricavate dalla stessa proiezione; le due valutazioni controller/shared possono ripetere le due query nella stessa risposta, senza query per singolo ruolo.

AppLayout continua a usare il team della rotta e mostra il suo ruolo dalla membership corrispondente, anche quando il team preferito ha privilegi maggiori. Se manca una membership per il team della pagina, la shell rimuove contenuto e navigazione privata. [TeamSwitcher](../resources/js/components/app/TeamSwitcher.tsx) è un form con select nativa, nome/ruolo per opzione e pulsante esplicito: cambiare il valore non invia il POST. La stessa selezione è adottata in Your teams, con preferenza come valore attivo; nessuna creazione di nuovi team viene introdotta. Account espone “Open dashboard” soltanto per il team risolto come accessibile, con ID ora incluso nella proiezione.

Il POST `/teams/{team}/select` continua a usare middleware, gate e SwitchTeam con lock/recheck correnti. HTML: redirect esplicito alla dashboard di quel team, senza riportare filtri/risorse del precedente. JSON: risposta 200 esatta `{ "destination": "/teams/{team}/dashboard" }` dopo il salvataggio, con no-store/private. Il client invia richiesta same-origin con CSRF e marcatore AJAX, verifica la destinazione attesa e rifiuta redirect, body malformati, destinazioni esterne o di un altro team. La successiva visita GET usa preserveState/preserveScroll false. Le viste private status page adottano NoStoreAuthentication anche per la nuova proiezione membership; le rotte pubbliche restano nel proprio gruppo.

Prima del POST la shell smonta contenuto e navigazione del vecchio team, nasconde il vecchio ruolo e disabilita ulteriori selezioni. Il contenuto realtime della dashboard è un figlio smontabile: chiusura della sottoscrizione, abort della lettura in corso e fence delle risposte tardive restano responsabilità della sessione esistente. Un diniego autorevole del recupero/realtime rimuove anche la shell privata e il selettore obsoleto, offrendo Your teams. Una revoca esterna viene rilevata al successivo controllo autorizzato previsto dal recupero esistente: questo task non aggiunge polling o nuovi eventi di revoca.

La selezione ha un limite di 10 secondi. Errore HTTP, rete persa, risposta inattesa, timeout o visita di destinazione non completata lasciano nascosti i dati precedenti e richiedono “Check current teams”, lettura esplicita di `/teams`. Non ripristinare per deduzione il team precedente: il POST potrebbe essere stato salvato senza consegnare la risposta. Nessun retry automatico al ritorno online; unmount abortisce il lavoro e un acknowledgement tardivo non naviga. Le proiezioni dell’header si aggiornano alle visite private complete: il recupero metrico parziale non viene trasformato in polling delle membership.

Il primo utilizzo in AppLayout riguarda ancora la dashboard, che non contiene draft di modifica del dominio. La migrazione dei form con guardia di abbandono/invio in corso resta UI.02.4 secondo i flussi definiti; non offrire lo stesso selettore in un form legacy senza prima collegare tale guardia. UI.02.3 aggiungerà il menu mobile, conservando la select nativa accessibile e le stesse regole di sospensione.

[TeamSwitcher.test.tsx](../tests/frontend/TeamSwitcher.test.tsx) copre conferma, trasporto/CSRF, ruolo per team, single-flight, errori HTTP/rete/JSON/destinazione, timeout, unmount/risposte tardive, preferenza assente/revocata, account e smontaggio/abort della vera dashboard realtime. [TeamNavigationTest.php](../tests/Integration/TeamNavigationTest.php) verifica payload consentiti, contesti esclusi, privacy, selezione HTML/JSON, revoca/isolamento e numero query del servizio su PostgreSQL. I test di selezione esistenti sono aggiornati al redirect dashboard e al form condiviso; risultati nel piano.

## Navigazione mobile — UI.02.3

[useDesktopNavigation](../resources/js/components/app/useDesktopNavigation.ts) osserva `(min-width: 1024px)` con matchMedia e useSyncExternalStore, rimuovendo il listener alla fine della sessione. Da 1024 CSS px AppLayout monta soltanto sidebar/TeamLinks; sotto soglia monta soltanto trigger/dialogo MobileNavigation. Gli ambienti DOM senza matchMedia e l’eventuale snapshot server mantengono il baseline desktop; il browser client osserva la propria larghezza effettiva, anche dopo reflow/zoom. Non duplicare sidebar e dialogo nascondendo soltanto una copia con CSS.

[MobileNavigation](../resources/js/components/app/MobileNavigation.tsx) usa `dialog.showModal()`: top layer modale, sfondo non interattivo e contenimento Tab/Shift+Tab sono nativi. Il trigger Open navigation espone aria-haspopup/dialog, expanded e controls; il dialogo è nominato dall’h2 Navigation. Focus iniziale su Close navigation; Escape/cancel e Close chiudono e ripristinano il trigger. La chiusura recupera lo stile overflow preesistente, senza sovrascrivere una precedente scelta del chiamante. Non sono aggiunti overlay con un proprio motore di focus, dipendenze, animazioni o fallback che presentino come modale un semplice div.

La superficie è opaca, larga al massimo min(22rem, 100vw), alta al massimo 100dvh e scorrevole, con intestazione/controlli che vanno a capo. Solo il backdrop privo di contenuti è traslucido. Il selettore team rimane un’unica istanza nell’header: non viene clonato o rimontato aprendo il dialogo. Lo sfondo è inerte mentre il menu è aperto; chiuderlo consente di usare il selettore con le regole pending/errore già implementate.

[TeamLinks](../resources/js/components/app/TeamLinks.tsx) condivide label, destinazioni e aria-current fra sidebar e dialogo. Un click ordinario chiude il dialogo e porta temporaneamente il focus al main; il successo della visita Inertia focalizza il nuovo h1 nel frame successivo. Il callback verifica che l’URL non sia nel frattempo cambiato. Click modificati per altra scheda mantengono il normale comportamento del browser senza chiudere il menu corrente. I breadcrumb e gli URL dei filtri non vengono riscritti.

Passaggio al desktop, sospensione per cambio team o diniego rimuovono il dialogo, ripristinano lo scrolling e spostano il focus al main ancora visibile, evitando un controllo mobile rimosso. Rientrare nel breakpoint mobile parte chiuso. Unmount libera anche il listener media-query; nessuna azione di chiusura annulla o ripete una mutazione team. AccountMenu si chiude anche quando il focus esce dalla disclosure, così un menu account lasciato aperto non intercetta Escape del successivo dialogo.

[MobileNavigation.test.tsx](../tests/frontend/MobileNavigation.test.tsx) aggiunge dieci casi di apertura/tastiera, cancel/close, focus, navigazione, click modificati, breakpoint, diniego, draft e cleanup. Il test double locale di showModal/close rende osservabile il lifecycle in jsdom, senza simulare il contenimento nativo del focus; i prototipi sono ripristinati dopo aver smontato le fixture. La suite completa mantiene anche i test team/realtime esistenti.

Prova browser mirata del 2026-11-10: eseguibile Brave headless con Chromium **157.0.8103.39**, profilo temporaneo e server loopback con sole risposte Inertia sintetiche e asset compilati. Verificati dialogo realmente `:modal`, nove Tab e Shift+Tab contenuti, impossibilità di focalizzare lo sfondo, Escape/ripristino, passaggio al desktop/focus main e focus h1 dopo navigazione. A 390 CSS px document width 390; a 195 CSS px document width 195. Zero eccezioni JS nel probe.

Verificato separatamente lo zoom **nativo 200%** tramite impostazione del solo profilo di prova: viewport 780 → 390 CSS px, devicePixelRatio 1 → 2, document width 390; dialogo modale largo 352 px e Close visibile. Ripristinato zoom 100%. È una prova reale di zoom browser, distinta dal test di reflow a 195 CSS px. Server e browser temporanei arrestati, nessuno screenshot nel repository e nessuna preferenza/dato del browser utente toccata. Queste prove non esercitano backend/sessioni reali né chiudono gli ID L: VoiceOver, Firefox e flussi completi restano UI.06 dopo UI.02.4/UI.03/UI.04. Esiti del gate e prossimo passo nel piano.

## Migrazione privata e protezione bozze — UI.02.4

AppLayout è ora adottato da dashboard, lista/creazione/modifica/dettaglio monitor, lista/dettaglio incidenti, notifiche, status page private, team e trasferimento proprietà. PrivateContextLayout distingue Account (overview, sicurezza, Your teams) da Platform administration (lista/dettaglio team): nessun team attivo o ruolo viene dedotto per il pannello operatore. I menu locali duplicati sono rimossi, conservando azioni, policy e collegamenti pertinenti alla risorsa. Le precedenti note «solo dashboard» descrivono le consegne storiche, superate da questa migrazione. Auth, inviti/onboarding e pubblico conservano il layout dedicato.

[NavigationGuard](../resources/js/components/app/NavigationGuard.tsx) è montato una volta fuori dal ciclo delle pagine Inertia. I form privati registrano solo flag dirty/busy; valori e credenziali restano nei componenti. useFormProtection aggiorna la baseline del form con setDefaults dopo un invio accettato: una modifica successiva torna protetta. Anche richieste fetch e riconferma password registrano il proprio stato pendente. Nessuna mutazione di dominio viene riprodotta dalla guardia.

Link ordinari, GET programmatiche, logout e selettore chiedono Stay/Discard tramite dialogo nativo quando esiste una bozza; Stay riceve il focus iniziale, Escape annulla e ripristina il focus. Dopo conferma viene riattivato il link originario, con i suoi callback e URL. Una richiesta pendente impedisce l’abbandono e spiega il motivo; prima di inviare il cambio team si attende la decisione. Reload/uscita documento usano beforeunload nativo. Il cambio confermato e i redirect di sicurezza autorevoli hanno un bypass esplicito limitato alla navigazione.

[historyNavigation](../resources/js/components/app/historyNavigation.ts) installa il dispatcher popstate **prima** che Inertia registri il proprio listener: l’ordine è necessario per evitare che Indietro smonti il form prima di Stay. Il dispatcher dura quanto la finestra e non trattiene dati di pagina; la delega del provider viene liberata al cleanup. La guardia aggiunge soltanto una posizione intera alla history, preservando lo stato opaco di Inertia; ripristina prima la voce sorgente, poi applica la decisione. I metodi nativi sono ripristinati al cleanup. Nessun campo viene copiato in history/storage dalla guardia.

Gli hook di pagina vivono nei figli rimovibili della shell: cambio team o diniego autorevole eliminano form, sessioni realtime e letture pendenti. TeamAccessContext propaga il diniego osservato da useLivePage; il layout rimuove dati, ruolo e selettore e mantiene il messaggio di accesso perso. Un diniego che smonta una bozza annulla anche un dialogo di abbandono già aperto. Le riconferme password esistenti e le autorizzazioni server restano autorevoli.

NavigationGuard.test copre bozze, successo e nuova modifica, richieste, switch, focus/cancel, history/cleanup, contesti account/piattaforma e revoca durante il dialogo. ## Lista monitor e ritorni — UI.03.3

Monitors/Index usa i controlli semantici per ricerca, select, pulsanti e paginazione condivisa, con DataTable e scrolling locale. Heartbeat distingue l’ingresso dei segnali da una destinazione assente; history precedenti senza destination mostrano dato indisponibile. Nessuna decrittazione o aggregazione nel client.

I filtri si applicano esplicitamente da pagina uno e le visite GET conservano voci della cronologia, senza replace. Ogni nuova selezione URL rimonta il solo contenuto della lista per riallineare gli input ai filtri accettati, anche su Indietro/Avanti; il refresh realtime degli stessi filtri conserva il testo in digitazione. Callback di tentativi precedenti non liberano un tentativo successivo.

Un errore temporaneo o una risposta non valida durante la ricerca mantiene input e righe precedenti, con avviso e nuovo invio esplicito; nessun retry automatico o diagnostica grezza. I listener exception/invalid intercettano solo mentre questa ricerca è attiva e vengono rimossi all’unmount. Risposte 401/403/404 propagano invece il diniego alla shell e rimuovono dati privati e controlli. Il normale feedback LiveUpdates resta indipendente. Team senza monitor, filtri senza risultati, pagina fuori intervallo, errore e quota piena hanno messaggi distinti. Permessi/quota di creazione restano quelli del server.

`withMonitorListReturn` costruisce i link GET dal risultato verso dettaglio/creazione; Show/Create/Edit ricevono `monitorListUrl` normalizzato e usano quel contesto per ritorno/cancellazione e breadcrumb disponibili. L’edit torna al dettaglio con la stessa origine lista. Il client non legge un redirect arbitrario dalla query. [MonitorListReturn](../app/Http/Navigation/MonitorListReturn.php) accetta solo `/teams/{team-autorizzato}/monitors`, massimo 2048 byte del valore, ricostruendo q/type/status/state/page con [MonitorListSelection](../app/Data/Monitoring/MonitorListSelection.php), condiviso con ListMonitorsRequest. Nessuno schema/host, altro team, percorso dettaglio/mutazione o backslash/controllo è ammesso. Chiavi ignote, valori invalidi, frammenti e livelli annidati vengono scartati; filtri ripetuti non scelgono un valore e returnTo duplicato/array ripiega sulla lista canonica. Assente/invalido torna alla prima pagina non filtrata.
